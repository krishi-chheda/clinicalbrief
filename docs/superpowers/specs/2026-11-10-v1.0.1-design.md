# ClinicalBrief v1.0.1 — design

Date: 2026-11-10. Status: draft for approval.

## Intent

v1.0 is live (clinicalbrief.vercel.app + clinicalbrief.onrender.com). v1.0.1 does two things:

1. **Patch updates**: close the known backlog and make the site describe itself truthfully again.
2. **Three new features** taken from the site's own "Not built yet" list:
   - an **accuracy evaluation** of the AI note pipeline,
   - **semantic search** (roadmap Phase 8b), kept only if it measurably beats keyword search,
   - a **de-identified research view** for the `researcher` role.

Why: ClinicalBrief is a portfolio flagship whose selling point is honesty. Today the site says "no accuracy figure is
shown until measured", Phase 8b says "kept only if it beats full-text search", and the researcher role is described
as "de-identified views are a later phase". v1.0.1 turns those three promises into measured, shipped results.

## Goals

- Every patch item below is closed, each with a test or a recorded check.
- A published, reproducible accuracy figure for note extraction, with its sample size, uncertainty and limits.
- A recorded keyword-vs-semantic comparison on a fixed question set, and a ship / don't-ship decision that follows it.
- Researchers see no direct identifiers anywhere in the app.
- Version reads 1.0.1 everywhere; a CHANGELOG lists what changed.

## Non-goals

- New hosting, paid services, or a hosted LLM. Patient text still only goes to models on the same machine.
- Clinical validation, regulatory claims, or a validated de-identification method.
- Turning the public demo back on (stays behind `NEXT_PUBLIC_DEMO_ENABLED`).
- Splitting the large frontend component (`ClinicalBriefApp.tsx`), beyond what a feature needs.

## Anti-goals (failure even if it "works")

- Any accuracy number without its sample size, labelling method and confidence interval next to it.
- Labels written by the same rules the pipeline uses (that measures nothing).
- Shipping semantic search because it was built, when the comparison says it isn't better.
- Calling the research view "anonymised" or "de-identified to a standard". It is "direct identifiers removed".
- Breaking the free-tier budget: Supabase DB is ~237 MB of 500 MB.

## Constraints (standing project rules)

- Python 3.12 only (`py -3.12`). Tests: SQLite suite + `TEST_PG=1` Postgres/RLS suite; pre-push gate (`.githooks/pre-push`)
  runs both plus `tsc`.
- Incremental changes, each with tests, each handed to the independent reviewer session after a pre-push run.
- The assistant never commits or pushes; the user does.
- No scripts that write to the live DB; schema changes are new numbered migrations the user applies in the Supabase SQL editor.
- Schema source of truth is `clinicalbrief-backend/migrations/*.sql`; the ORM must match (drift test).
- Hosted API (Render) cannot reach a local model: any model-dependent feature must degrade to a labelled fallback online.

## Part B — Accuracy evaluation of note extraction

**What is measured:** the rule-based note pipeline (`ai_pipeline.py`, default mode), on its actual outputs: entity
spans with type (condition/finding, medication, allergy…), negation, family-history attribution, and ICD-10 suggestion.
The extractive summary is not scored (no meaningful reference).

**Labelled set:**
- ~50 notes sampled from the 35,103 in the DB, stratified across note types and patients, fixed seed, sample list
  committed. Exported once to a local file (read-only query; no DB writes).
- Gold labels in `clinicalbrief-backend/eval/gold/*.jsonl`: per note, every clinically relevant mention with span,
  type, negated yes/no, subject (patient/family).
- **Who labels: OPEN — see Questions.** Labels must not come from running the pipeline.
- A tiny labelling guideline (`eval/GUIDELINE.md`) so labels are consistent and the method is publishable.

**Metrics:** precision, recall, F1 per entity type and overall; strict (exact span+type) and lenient (overlap+type);
negation accuracy on matched entities; family-history accuracy; ICD-10 suggestion precision on matched conditions.
95% bootstrap confidence intervals. Error list (top false positives / false negatives) for the README.

**How it runs:** `py -3.12 -m app.cli eval-extraction` reads the gold files, runs the pipeline in-process (no DB),
prints a table and writes `eval/results/extraction-<date>.json`. A pytest test runs it on 2 tiny fixture notes so the
scorer itself is tested (a known-answer test for the metric code).

**Where it shows:** README status table row "Evaluation" moves from Not built to Prototype with the numbers;
a section on the public Data page (or Docs) with the table, n, CI, method and limits ("Synthea notes are templated;
this does not predict performance on real clinical text").

## Part C — Semantic search (Phase 8b), gated

Built in two stages so nothing ships unless it earns it.

**Stage 1 — offline comparison (always done).**
- Fixed question set: ~30 natural-language queries (e.g. "patients whose blood pressure medication was changed",
  "shortness of breath on exertion") with judged relevant notes, in `eval/search/questions.jsonl`. Judging covers the
  pooled top-10 of both methods per query.
- Keyword side: the existing `record_search` full-text query, **on Postgres** (on SQLite it is an unranked substring
  match, so ranking metrics would be meaningless). The corpus is copied once into the local test Postgres (pgserver) by
  a read-only export command the user runs against live; no writes to live.
- Corpus: all 35,103 notes (embedding runs on the local RTX 5070 through Ollama; minutes, not hours). Stated in the results.
- Semantic side: a **local** embedding model through Ollama (my call: `nomic-embed-text`, ~270 MB, not yet installed),
  one vector per note (truncated to the model's context), computed in memory over the notes in scope, no DB storage.
- Metrics: recall@10, nDCG@10, MRR, per method and for a hybrid (keyword ∪ semantic, reciprocal-rank fusion).
- Decision rule (written before running): ship only if semantic or hybrid beats keyword on nDCG@10 by ≥ 0.05 with the
  bootstrap CI excluding 0. Result goes on the roadmap either way.

**Stage 2 — only if Stage 1 says ship.**
- Storage: pgvector in Supabase, `halfvec(768)` per note (~1.5 KB × 35k ≈ 54 MB + index). New migration `0013`.
  Must fit the 500 MB budget with room left; measure after.
- Embedding happens locally (CLI `embed-notes`), the user runs it against the live DB the same way imports are run.
- Query embedding needs the local model: on Render it is unavailable, so the search page says "semantic ranking needs
  the local model; showing keyword results" (same pattern as Copilot's labelled fallback). Locally, a "Semantic / Hybrid"
  toggle on `/search`.
- Same scoping rules as today (allowed patient ids applied before ranking; researchers get no note text).

If Stage 1 says don't ship: roadmap Phase 8b → "tested, not adopted" with the numbers. That is a valid, honest outcome.

## Part D — De-identified research view

**Today:** researchers can read all records; search hides note text; the note view shows regex-redacted text. Patient
names, dates of birth, the knowledge-graph patient label, entity evidence sentences and Copilot citations are not
de-identified. `clinical_privacy.py` has a hard-coded `known_names` list ("John Smith"…) that does nothing useful.

**Change:** one server-side choke point so the frontend cannot leak what the API never sends.
- Patient identity for researchers: name → stable pseudonym (`Patient 3F9A…`, HMAC of patient id with a server
  secret), date of birth → birth year (or age band), address/contact fields omitted. Applies to patient list, patient
  record, graph label, review/governance views, search results, FHIR (researchers already can't export).
- Free text for researchers (note text, evidence sentences, snippets, Copilot citations): existing regex redaction
  **plus** the patient's own first/last name and the other names on their record, matched case-insensitively as whole
  words. Remove the hard-coded `known_names`.
- Copilot for researchers: answers and citations pass through the same redaction (my call; alternative is to refuse
  Copilot to researchers — see Questions).
- UI: a small persistent badge for researchers, "Direct identifiers removed — not a validated de-identification".
- Staff identities: researchers are not in the review or governance role sets, so reviewer emails are not exposed to
  them today; the endpoint test asserts that stays true.
- Tests: a researcher request to every patient-returning endpoint contains neither the patient's name nor full DOB
  (parametrised over endpoints, on SQLite and Postgres).

format, which nearest Tailwind token replaces each broken shade, chart/table styling on the public page.

## Calls made by the assistant (check these)

- Version string is semver `1.0.1` (displayed "v1.0.1"), since `package.json` requires semver.
- Embedding model `nomic-embed-text` via Ollama; `halfvec` storage to stay inside the free tier.
- Semantic search decision threshold: nDCG@10 +0.05, CI excluding 0.
- Nonce CSP accepted even though pages become dynamic, with TTFB measured.
- Researchers keep Copilot, with redaction.
- Part D's guarantee covers the database too, via P-9 (revoke direct table access), since the frontend never uses it.
- Search comparison runs on a local Postgres copy of all notes, exported read-only by the user.

## Questions for the user

- Who labels: unanswered; default taken = assistant drafts labels, author reviews; published as "AI-drafted, pending author review" until reviewed.

## Addendum (2026-11-13): v1.0.1 round 2

User chose "C" (both A and B, reported separately) and all four items. Demo work (D-01, Turnstile) waits.

1. **Extractor recall, two parts reported separately.**
   - **A. Independent vocabulary.** Dictionary terms from sources Synthea does not use: ICD-10-CM descriptions (CMS,
     April 2026, public domain) for diseases and symptoms (chapter R = Symptom), RxNorm ingredient names (NLM RxNav,
     `tty=IN`) for medications. Normalised (qualifiers such as ", unspecified" removed; too-generic terms dropped).
     A derived term list is committed so deployment needs no download. Matching by n-gram lookup (tens of thousands of
     terms). Matched diseases get their ICD-10-CM code as the suggestion. Measured on the same 40 notes; adopted as
     the default only if lenient precision stays >= 0.85 (decided before the run). Procedures keep the small list.
   - **B. Record linking.** For a note, the patient's own coded conditions, medications, procedures and allergies that
     the note mentions, shown in the note view as "In this patient's record". Read-only endpoint, no new table.
     Reported as coverage, explicitly not as accuracy (circular on Synthea: notes are rendered from the record).
2. **Negation set.** ~25 hand-written short notes exercising negation, family history and allergies, with labels per
   GUIDELINE.md; written by the AI model and published as such. Scored with the same scorer (`--set negation`).
3. **Signed-in browser checks** of the research view and Match meaning search (user signs in; researcher role and
   migrations applied by the user).
4. **Label review aid**: a generated side-by-side review page (gitignored, contains note text) and a command that
   records `reviewed_by` once the author has checked the labels.
